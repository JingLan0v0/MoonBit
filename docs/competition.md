## 3. 赛事概况、参与方式和方向

**【官网已确认】** 赛事在线进行，面向对 MoonBit、AI 辅助编程、开源和基础软件感兴趣的开发者，不限学生或社会人士。项目应面向实际需求，可运行、可测试、可维护。

允许原创项目、成熟生态库的 MoonBit 移植，以及已有项目的本期实质新增。官方强调边界、测试、文档、可维护性和真实可用性，没有在本次读取的主页中给出强制代码行数。

| 官网方向 | 涵盖内容 | 本次选择 |
| --- | --- | --- |
| 工具库 | 通用库、协议库、基础组件 | 否 |
| 数据处理 | 数据库、分析、数据及内容处理 | 是：MoonRow CSV 快照差异比较 |
| AI 应用 | 解决实际需求的 AI 开源应用 | 否 |
| 开发者工具 | CLI、解释器、运行时、LSP 等 | 作为产品形态参考，不另报第二个项目 |

方向用于启发选题，不构成选题限制。一个项目同时具备库和 CLI，不应拆成多个项目重复申领奖励。[依据：官网方向与验收](https://moonbitlang.github.io/Hackathon2026/#directions)。

### 6.2 一页项目说明准备内容

**【内部交付标准】** 使用项目方案第 10 节草稿，压缩成一页，至少说明项目名称、数据处理方向、真实问题、MoonBit 实现范围、功能边界、验收方法、交付物和计划时间，并填写真实参赛者与仓库信息。

**【待核实】** 官网只说“一页项目说明”，没有在已读摘要中明确必须是 PDF、指定模板、页尺寸或文件大小。实际提交格式以本期表单/章程为准；可以后续制作一页 PDF 备用，但本轮尚未制作，不把其他赛事要求直接套用。

### 6.3 身份与联系方式

**【内部交付标准】** 提前准备用户真实姓名或队伍名、GitHub ID、常用邮箱/联系方式和项目链接。具体必填字段由实际表单决定，不伪造、不替用户猜填身份资料。与支付有关的敏感资料只在官方明确要求的渠道填写，不放入公开仓库。

## 7. 开发过程应该保留什么

- [ ] 确定公开仓库并记录创建日期和项目起点。
- [ ] 将解析器、比较引擎、CLI、测试、文档分别作为明确任务跟踪。
- [ ] 随实际进展提交能解释目的的变更，及时推送，形成可追踪历史。
- [ ] 用 Issues 记录需求、缺陷和验收反馈；用 PR 保留适当的变更审阅过程。
- [ ] 更新 CHANGELOG 与进度交接说明，保存关键设计理由。
- [ ] 保存编译、测试与 CI 的实际结果，失败也如实处理。
- [ ] 记录第三方来源、许可证和 AI 辅助范围。

不能在最后一天伪造几天的提交记录，不能写尚未运行的测试“已经通过”。手写源码、生成产物、样例和文档应能够清楚区分。

## 9. 内部提交前自检

以下检查是我们的交付把关，不代表做完就自动获得官方验收通过。

### 9.1 工程检查

- [ ] 在独立干净目录按 README 从头构建，不使用开发目录中未提交的隐藏文件。
- [ ] 记录实际 MoonBit、Node.js 与依赖版本；构建步骤在 Windows 可执行。
- [ ] Linux CI 运行同一核心测试；未验证的平台不标注已支持。
- [ ] 主演示严格得到新增 1、删除 1、修改 1、未变化 2、变更字段 1。
- [ ] 行列重排不制造差异；组合键不碰撞；重复主键不会被覆盖。
- [ ] 非法 CSV、找不到文件、超限输入得到可解释错误。
- [ ] 独立启动最终产物验证退出码 0、1、2。
- [ ] JSON 输出可以解析，字符串不丢失；三种报告结论一致。
- [ ] 独立示例能导入 MoonBit 公共包。
- [ ] 输入规模限制与实测一致，不填写虚构性能、覆盖率或测试成绩。

### 9.2 材料检查

- [ ] README 命令、源码版本、测试记录和演示产物是同一版。
- [ ] 公开链接可访问；未提交文件不会成为复现前提。
- [ ] LICENSE、第三方声明、引用来源完整。
- [ ] 用户能够解释项目的主要设计和限制。
- [ ] 查验最新正式章程与群公告，没有遗漏新增要求。
- [ ] 按确认的验收渠道提交，并保存时间、版本、附件与回执。
- [ ] 需要补件时仍在官方允许的窗口内完成。
